# Запуск новой версии на barteron.club

Как выложить Barteron nextgen сначала на тест, потом на прод, и как вернуть старую версию. Написано 11.11.2026. Ничего из этого ещё не выполнялось: пуш в репозиторий и всё, что касается серверов, делается только с разрешения владельца проекта.

## Как выкладывается старая версия

По `.github/workflows/` репозитория [pocketnetteam/barteron.gui](https://github.com/pocketnetteam/barteron.gui) и по ответам серверов (проверено снаружи 11.11, только чтение):

|                       | Тест                            | Прод                            |
| --------------------- | ------------------------------- | ------------------------------- |
| Адрес                 | test.barter.pocketnet.app       | barteron.club                   |
| Ветка                 | `dev`                           | `main`                          |
| Раннер GitHub Actions | `test`                          | `mirror.barteron.club`          |
| Папка на сервере      | `/docker/barter/`               | `/data/barteron/`               |
| Сборка                | `yarn build`, SDK с bastyon.com | `yarn build`, SDK с bastyon.com |
| Веб-сервер            | nginx 1.21.6, PHP 7.4.33        | Caddy, PHP 8.2.28               |

Шаги workflow: Node 18, `yarn install`, `yarn build`, затем `rm -rf <папка>/*` и `rsync -ah ./dist/ <папка>/`. Тестовый стенд собирается так же, как прод: `.env.test` старого репозитория (SDK с test.pocketnet.app) workflow не использует.

На обоих серверах любой путь, которого нет среди файлов, открывает `index.php`, и PHP подставляет в страницу теги превью. К ноде он ходит по адресу `http://proxy:8898/`. Что ещё видно снаружи:

- На проде превью профиля пришло с данными из ноды. Значит, curl в PHP есть и нода доступна.
- На тесте то же превью пришло с тегами по умолчанию: либо PHP там не достаёт до ноды, либо ходит в ноду тестовой сети.
- На проде ошибки PHP выводятся прямо в страницу. Если в запросе нет заголовка языка, старый `og.php` печатает в `<head>` предупреждение с путём `/var/www/barteron.club/og.php`. Новый `og.php` предупреждений не печатает, это проверяет og-check.
- PHP прода работает из `/var/www/barteron.club/`, а раннер копирует в `/data/barteron/`. Видимо, это одна и та же папка, подключённая в контейнер.

## Что меняется для сервера

Ничего. Новая сборка повторяет старый набор файлов:

- `index.php`: страница приложения плюс теги превью. Его собирает плагин [build/index-php.ts](build/index-php.ts) из `index.html`, а `index.html` в сборку не попадает, как и раньше.
- `og.php` и `rpc.php`: превью для объявления, обмена, сделки, модерации и профиля. Исходники — [php/](php/). Ссылки и тексты те же, ошибки старых файлов исправлены (PLAN.md, этап 11).
- `b_manifest.json`, иконки (`b_icon.png`, `s_icon.png`, `m_icon.png`), `miniapp-service-worker.js`, `docs/`. Файлы приложения лежат в `assets/` (у старой версии были `js/`, `css/`, `img/`).

`api.php` не переносили: старый `og.php` его подключал, но ни разу не вызывал.

Требования: PHP 7.0 или новее с расширением curl, оба сервера подходят. Для сборки нужны Node 20.19 или новее и pnpm 10. Новые workflow ставят Node 22 и берут версию pnpm из `package.json`.

## Что решили 11.11

1. **Код живёт в ветке `nextgen` репозитория pocketnetteam/barteron.gui.** Раннеры уже подключены к этому репозиторию. Workflow лежат в [.github/workflows/](.github/workflows/) под теми же именами файлов, что у старых, поэтому при слиянии в `main` новые файлы заменят старые:
   - `test.barter.pocketnet.app.yml`: пуш в `nextgen` → `pnpm check`, `pnpm build`, копия в `/docker/barter/`;
   - `barteron.club.yml`: пуш в `main` → `pnpm check`, `pnpm build`, снимок текущей версии, копия в `/data/barteron/`. При ручном запуске из другой ветки задание не выполнится, так что до прода дойдёт только `main`.

   Пока `nextgen` не слита в `main`, старые workflow в `main` и `dev` работают как раньше. Для пуша нужен доступ на запись в barteron.gui.

2. **Сервер проверен снаружи** (см. выше). У администратора осталось подтвердить два пункта:
   - `/data/barteron/` — та же папка, из которой работает PHP прода;
   - раннер прода может создавать папки в `/data/` (туда ляжет снимок для отката).

3. **Автор коммитов** — `xen <xen@mail.com>`, как в bastyon-nextgen.

Ещё открыто: правки нового Bastyon ([HOST-TASKS.md](HOST-TASKS.md)), если он уже у пользователей:

## Как сделать ветку

У истории barteron-nextgen нет общих коммитов с barteron.gui, и GitHub не откроет pull request из такой ветки в `main`. Слияние стратегией `ours` соединяет обе истории и оставляет только файлы новой версии:

```sh
# в barteron-nextgen, на main
git remote add gui https://github.com/pocketnetteam/barteron.gui
git fetch gui
git merge -s ours --allow-unrelated-histories gui/main -m "Barteron nextgen вместо старой версии"
git push gui main:nextgen
```

После этого работа продолжается в `main` barteron-nextgen. Каждый `git push gui main:nextgen` выкладывает версию на тестовый стенд.

Проверено 11.11 на временной копии barteron.gui:

- после слияния файлы те же, что в barteron-nextgen;
- pull request из `nextgen` в `main` даёт файлы новой версии;
- `git revert -m 1` этого слияния в `main` возвращает старую версию целиком, вместе со старыми workflow;
- ветка из чистой копии проходит `pnpm install --frozen-lockfile`, `pnpm check` и `pnpm build`.

## Порядок

### 1. Тестовый стенд

1. Пуш в `nextgen` (см. «Как сделать ветку»), дальше workflow соберёт и выложит сам.
2. Проверить:
   - превью: `curl -s https://test.barter.pocketnet.app/barter/<txid> | grep og:`. Теги должны быть на месте и без предупреждений PHP. Название объявления на тесте может не прийти (см. выше);
   - список паритета (PLAN.md, приложение B) в прежнем Bastyon и в новом, на компьютере и телефоне. Прежний Bastyon до сих пор не проверялся ни разу (PLAN.md, риск 7);
   - запись в сеть: объявление, правка, снятие, профиль, отзыв, оценка, безопасная сделка с переводом, заявка на модерацию. Сеть выбирает Bastyon, в котором открыт стенд, а не сборка: если открыть стенд из bastyon.com, запись уйдёт в основную сеть. Поэтому сначала выяснить, из какого Bastyon открывается стенд и можно ли открыть его из test.pocketnet.app (PLAN.md, риск 6);
   - ссылку из чата `…/application?id=barteron.pocketnet.app&p=<путь в hex>`: она должна открыть нужный экран.

### 2. Прод

1. Pull request из `nextgen` в `main` barteron.gui и слияние. Workflow `barteron.club` сам соберёт версию, сделает снимок текущей `/data/barteron-old-<дата-время>` и скопирует новую. Путь снимка будет в логе шага «Keep the current version».
   - Если у раннера нет прав создать папку в `/data/`, шаг упадёт и до копирования дело не дойдёт: на сервере ничего не изменится. Тогда нужно дать раннеру права или поменять путь снимка в workflow.
2. Копирование идёт **без `rm -rf`**. Старые `js/`, `css/` и `img/` остаются на сервере, поэтому у тех, кто держит старую версию открытой, она не сломается на подгрузке экрана. `index.php` заменяется, и каждое новое открытие получает новую версию. Старые файлы и снимки удалять вручную, не раньше чем через неделю.
3. Сразу после выкладки проверить по одному запросу, без циклов. 11.11 после шести запросов за минуту barteron.club минут на десять перестал отвечать моему адресу, похоже на ограничение частоты.
   - `curl -sI https://barteron.club/` → 200;
   - `curl -s https://barteron.club/barter/<txid> | grep og:` → название объявления;
   - открыть в обоих Bastyon, на компьютере и телефоне: главная, объявление, профиль, сделка по ссылке из чата;
   - в логе ошибок PHP нет строк `Barteron link preview:`.

### 3. Откат

**Когда:** приложение не открывается в одном из Bastyon, не проходит запись в сеть или пользователи массово жалуются.

**Быстро, файлами:** `rsync -ah --delete /data/barteron-old-<дата-время>/ /data/barteron/`, путь берётся из лога выкладки. Старая версия возвращается целиком за секунды. Но в `main` остаётся новая версия, и следующий пуш в `main` выложит её снова. Поэтому после такого отката в `main` не пушат, пока не решат, что дальше, или откатывают ещё и в git.

**Через git:** в `main` сделать `git revert -m 1 <коммит слияния pull request>` и запушить. Вернутся старые файлы вместе со старым workflow, и он выложит старую версию так же, как раньше (Node 18, `yarn build`, `rm -rf`). Просто перезапустить старый прогон на GitHub не выйдет: перезапуск доступен 30 дней, а последний коммит старой версии в `main` — от 11.06.2026.

**Что увидят пользователи:**

- Данные в сети общие. Объявления, профили, отзывы и сделки, созданные новой версией, старая показывает: форматы транзакций те же, новые поля только добавлены.
- Валюта, место и избранное хранятся на устройстве под старыми ключами и в старом формате, поэтому они сохранятся.
- Черновики, список сделок устройства, тема и отложенное продление лежат под новыми ключами. Старая версия их не видит, при повторном переключении они вернутся.
- Если новая версия открыта в момент отката, то при переходе на ещё не загруженный экран появится «Вышла новая версия». После перезапуска откроется старая.

## Проверка превью без сервера

```sh
pnpm build
node build/og-check.mjs --php <путь к php>
```

Скрипт поднимает поддельную ноду, отдаёт `dist/` через встроенный сервер PHP и проверяет 19 ссылок: объявление, обмен, сделку, модерацию, профиль, разметку в названии, ссылку с массивами, зависшую ноду. В сеть он не ходит. Прогнан на PHP 7.4 и 8.3, на серверах стоят 7.4.33 и 8.2.28.
