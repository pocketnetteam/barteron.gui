# Запуск новой версии на barteron.club

Как выложить Barteron nextgen сначала на тест, потом на прод, и как вернуть старую версию. Написано 11.11.2026, раздел про открытие стенда и ветку `barteron-nextgen` — 12.11. Ветка запушена 12.11, выкладок ещё не было. Всё, что касается серверов, делается только с разрешения владельца проекта.

## Как выкладывается старая версия

По `.github/workflows/` репозитория [pocketnetteam/barteron.gui](https://github.com/pocketnetteam/barteron.gui) и по ответам серверов (проверено снаружи 11.11, только чтение):

|                       | Тест                            | Прод                            |
| --------------------- | ------------------------------- | ------------------------------- |
| Адрес                 | test.barter.pocketnet.app       | barteron.club                   |
| Ветка                 | `dev`                           | `main`                          |
| Раннер GitHub Actions | `test`                          | `mirror.barteron.club`          |
| Папка на сервере      | `/docker/barter/`               | `/data/barteron/`               |
| Сборка                | `yarn build`, SDK с bastyon.com | `yarn build`, SDK с bastyon.com |
| Веб-сервер            | nginx 1.21.6, PHP 7.4.33        | Caddy, PHP 8.2.28               |

Шаги workflow: Node 18, `yarn install`, `yarn build`, затем `rm -rf <папка>/*` и `rsync -ah ./dist/ <папка>/`. Тестовый стенд собирается так же, как прод: `.env.test` старого репозитория (SDK с test.pocketnet.app) workflow не использует.

На обоих серверах любой путь, которого нет среди файлов, открывает `index.php`, и PHP подставляет в страницу теги превью. К ноде он ходит по адресу `http://proxy:8898/`. Что ещё видно снаружи:

- На проде превью профиля пришло с данными из ноды. Значит, curl в PHP есть и нода доступна.
- На тесте то же превью пришло с тегами по умолчанию: либо PHP там не достаёт до ноды, либо ходит в ноду тестовой сети.
- На проде ошибки PHP выводятся прямо в страницу. Если в запросе нет заголовка языка, старый `og.php` печатает в `<head>` предупреждение с путём `/var/www/barteron.club/og.php`. Новый `og.php` предупреждений не печатает, это проверяет og-check.
- PHP прода работает из `/var/www/barteron.club/`, а раннер копирует в `/data/barteron/`. Видимо, это одна и та же папка, подключённая в контейнер.

## Что меняется для сервера

Ничего. Новая сборка повторяет старый набор файлов:

- `index.php`: страница приложения плюс теги превью. Его собирает плагин [build/index-php.ts](build/index-php.ts) из `index.html`, а `index.html` в сборку не попадает, как и раньше.
- `og.php` и `rpc.php`: превью для объявления, обмена, сделки, модерации и профиля. Исходники — [php/](php/). Ссылки и тексты те же, ошибки старых файлов исправлены (PLAN.md, этап 11).
- `b_manifest.json`, иконки (`b_icon.png`, `s_icon.png`, `m_icon.png`), `miniapp-service-worker.js`, `docs/`. Файлы приложения лежат в `assets/` (у старой версии были `js/`, `css/`, `img/`).

`api.php` не переносили: старый `og.php` его подключал, но ни разу не вызывал.

Требования: PHP 7.0 или новее с расширением curl, оба сервера подходят. Для сборки нужны Node 20.19 или новее и pnpm 10. Новые workflow ставят Node 22 и берут версию pnpm из `package.json`.

## Как открыть тестовый стенд в Bastyon (решили 12.11)

Barteron зашит в оба Bastyon с id `barteron.pocketnet.app` и адресом `barteron.club`. С `test.barter.pocketnet.app` новый Bastyon этот id не примет. Поэтому сборка стенда (`BARTERON_STAND=test` в его workflow) отдаёт `b_manifest.json` с id `barterontest.app` и названием «Barteron (test)». Всё остальное в ней такое же, как в проде. Проверяющий подключает стенд у себя:

- **новый Bastyon:** «Сервисы» → «Для разработчиков: открыть своё приложение» → `https://test.barter.pocketnet.app` → «Загрузить»;
- **прежний Bastyon:** `https://bastyon.com/devapplications` → «Создать приложение». Поля: id `barterontest.app`, адрес `test.barter.pocketnet.app`, остальное — как в манифесте. Кнопку «Публиковать» не нажимать: она записывает приложение в сеть.

Стенд виден только на том устройстве, где его подключили. В сеть ничего не пишется, в каталог приложений он не попадает. Оба пути найдены по коду хостов. Вживую их можно проверить только после первой выкладки на стенд, когда он отдаст новый манифест.

**Запись в сеть со стенда:**

- в прежнем Bastyon работает сразу, он пускает `barteron.*` к любому приложению с правом `account`;
- в новом Bastyon — после [HOST-TASKS.md](HOST-TASKS.md), п. 8, до него стенд только читает;
- уходит в сеть того Bastyon, где открыт стенд. Из bastyon.com это основная сеть, поэтому писать со своих тестовых аккаунтов и снимать всё после проверки.

**Почему не регистрация в каталоге сети.** Записать приложение в каталог можно только из прежнего Bastyon, кнопкой «Публиковать». По коду ноды (`pocketnet.core`, ветка 0.22) и прежнего Bastyon:

- запись сразу видна в «Сервисах» у всех пользователей;
- прежний Bastyon предупреждает, что в основной сети публикация стоит 50 PKOIN;
- в основной сети один аккаунт регистрирует одно приложение, и удаление место не освобождает. Править запись можно;
- id — до 20 символов: латиница, цифры, `.` и `_`, уникальный на всю сеть. `barteron.pocketnet.app` длиннее, поэтому Barteron и не в каталоге, а зашит в Bastyon. `barterontest.app` проходит, если когда-нибудь понадобится;
- новый Bastyon прячет записи каталога с названием или адресом встроенного приложения, так что назвать её «Barteron» нельзя;
- убрать запись из каталога может только автор, транзакцией удаления (в прежнем Bastyon — «Удалить» на странице приложения). Ещё её могут скрыть модераторы по жалобам.

Каталог понадобится, только если позовём много сторонних проверяющих, которым неудобно вводить адрес.

**Ещё открыто:** пользуется ли кто-то `test.barter.pocketnet.app` для старой версии. Старый workflow выкладывает туда ветку `dev`, новый — `barteron-nextgen` по ручному запуску, в ту же папку `/docker/barter/`. Первый же запуск заменит там старую версию. Если стенд занят, нужен отдельный адрес: DNS, сайт на сервере и папка для раннера. Это работа администратора, потом в workflow и в `STANDS` (`build/manifest.ts`) меняется адрес.

## Как сделать ветку

Сделано 12.11. У истории этого репозитория не было общих коммитов с barteron.gui, и GitHub не открыл бы pull request из такой ветки в `main`. Слияние стратегией `ours` соединяет обе истории и оставляет только файлы новой версии. Прод решили выкладывать из самой ветки, но возможность pull request в `main` осталась:

```sh
# в этом репозитории, на main
git remote add gui https://github.com/pocketnetteam/barteron.gui
git fetch gui
git merge -s ours --allow-unrelated-histories gui/main -m "Barteron nextgen вместо старой версии"
git push gui main:barteron-nextgen
```

Работа продолжается в локальной `main`, обновление ветки — `git push gui main:barteron-nextgen`. Пуш ничего не выкладывает (см. «Что решили»). История старой версии теперь тоже в `git log`, свою видно через `git log --first-parent`.

Проверено 11.11 на временной копии barteron.gui:

- после слияния файлы те же, что в новой версии;
- pull request из ветки в `main` даёт файлы новой версии;
- `git revert -m 1` этого слияния в `main` возвращает старую версию целиком, вместе со старыми workflow;
- ветка из чистой копии проходит `pnpm install --frozen-lockfile`, `pnpm check` и `pnpm build`.

## Порядок

### 1. Тестовый стенд

1. Выяснить, свободен ли стенд (см. «Как открыть тестовый стенд в Bastyon»). Потом запустить workflow вручную: GitHub → Actions → test.barter.pocketnet.app → Run workflow → ветка `barteron-nextgen` (или `gh workflow run test.barter.pocketnet.app.yml --ref barteron-nextgen`). Кнопка есть, потому что у старого файла в `main` тоже есть ручной запуск, а выполняется файл из выбранной ветки. Если стенд будут выкладывать часто, в workflow возвращается запуск по пушу.
2. Проверить:
   - манифест, одним запросом: `curl -s -D - -H 'Origin: https://bastyon.com' https://test.barter.pocketnet.app/b_manifest.json`. В ответе должны быть id `barterontest.app` и заголовок `Access-Control-Allow-Origin`. Без заголовка Bastyon в браузере не загрузит манифест, и подключить стенд не выйдет. Тогда администратор добавляет заголовок для этого файла в настройки nginx стенда;
   - превью: `curl -s https://test.barter.pocketnet.app/barter/<txid> | grep og:`. Теги должны быть на месте и без предупреждений PHP. Название объявления на тесте может не прийти (см. выше);
   - список паритета (PLAN.md, приложение B) в прежнем Bastyon и в новом, на компьютере и телефоне. Прежний Bastyon до сих пор не проверялся ни разу (PLAN.md, риск 7);
   - запись в сеть: объявление, правка, снятие, профиль, отзыв, оценка, безопасная сделка с переводом, заявка на модерацию. Сеть выбирает Bastyon, в котором открыт стенд, а не сборка: если открыть стенд из bastyon.com, запись уйдёт в основную сеть. В новом Bastyon запись заработает после HOST-TASKS, п. 8 (PLAN.md, риск 6);
   - ссылки из чата (`…/application?id=barteron.pocketnet.app&p=<путь в hex>`) ведут в barteron.club, а не на стенд. Их проверяют на проде.

### 2. Прод

1. В `barteron-nextgen`: коммит, который в `barteron.club.yml` меняет `main` на `barteron-nextgen` в двух местах, в `on.push.branches` и в условии `if`. Пуш этого коммита и выкладывает прод. Workflow сам соберёт версию, сделает снимок текущей `/data/barteron-old-<дата-время>` и скопирует новую. Путь снимка будет в логе шага «Keep the current version».
   - Если у раннера нет прав создать папку в `/data/`, шаг упадёт и до копирования дело не дойдёт: на сервере ничего не изменится. Тогда нужно дать раннеру права или поменять путь снимка в workflow.
   - До этого в `main` убрать из старого `barteron.club.yml` блок `push:`, оставить `workflow_dispatch:`. Сам этот пуш ничего не выложит: GitHub берёт файл из запушенного коммита, а в нём запуска по пушу уже нет. Иначе любой пуш в `main` выложит поверх старую версию, с `rm -rf`. Выключить старый workflow кнопкой в Actions нельзя: GitHub считает оба файла одним workflow, потому что путь у них общий, и выключится и новый.
2. Копирование идёт **без `rm -rf`**. Старые `js/`, `css/` и `img/` остаются на сервере, поэтому у тех, кто держит старую версию открытой, она не сломается на подгрузке экрана. `index.php` заменяется, и каждое новое открытие получает новую версию. Старые файлы и снимки удалять вручную, не раньше чем через неделю.
3. Сразу после выкладки проверить по одному запросу, без циклов. 11.11 после шести запросов за минуту barteron.club минут на десять перестал отвечать моему адресу, похоже на ограничение частоты.
   - `curl -sI https://barteron.club/` → 200;
   - `curl -s https://barteron.club/barter/<txid> | grep og:` → название объявления;
   - открыть в обоих Bastyon, на компьютере и телефоне: главная, объявление, профиль, сделка по ссылке из чата;
   - в логе ошибок PHP нет строк `Barteron link preview:`.

### 3. Откат

**Когда:** приложение не открывается в одном из Bastyon, не проходит запись в сеть или пользователи массово жалуются.

**Быстро, файлами:** `rsync -ah --delete /data/barteron-old-<дата-время>/ /data/barteron/`, путь берётся из лога выкладки. Старая версия возвращается целиком за секунды. Но следующий пуш в `barteron-nextgen` выложит новую снова. Поэтому после такого отката в ветку не пушат, пока не решат, что дальше.

**Сборкой старой версии:** GitHub → Actions → barteron.club → Run workflow → ветка `main`. Выполнится старый файл из `main`, и он выложит старую версию так же, как раньше (Node 18, `yarn build`, `rm -rf`). Просто перезапустить старый прогон на GitHub не выйдет: перезапуск доступен 30 дней, а последний коммит старой версии в `main` — от 11.06.2026.

**Что увидят пользователи:**

- Данные в сети общие. Объявления, профили, отзывы и сделки, созданные новой версией, старая показывает: форматы транзакций те же, новые поля только добавлены.
- Валюта, место и избранное хранятся на устройстве под старыми ключами и в старом формате, поэтому они сохранятся.
- Черновики, список сделок устройства, тема и отложенное продление лежат под новыми ключами. Старая версия их не видит, при повторном переключении они вернутся.
- Если новая версия открыта в момент отката, то при переходе на ещё не загруженный экран появится «Вышла новая версия». После перезапуска откроется старая.

## Проверка превью без сервера

```sh
pnpm build
node build/og-check.mjs --php <путь к php>
```

Скрипт поднимает поддельную ноду, отдаёт `dist/` через встроенный сервер PHP и проверяет 19 ссылок: объявление, обмен, сделку, модерацию, профиль, разметку в названии, ссылку с массивами, зависшую ноду. В сеть он не ходит. Прогнан на PHP 7.4 и 8.3, на серверах стоят 7.4.33 и 8.2.28.
